# Prime P1 Shell + Compositor v1

Status: **P1 IMPLEMENTATION CONTRACT — DEPENDENCY LOCK/LIVE PROOF REQUIRED**

Authority: `docs/adr/ADR-0001-P1-SYSTEM-FOUNDATION.md`, `docs/PRIME_OS_MASTER_PLAN.md`, and `docs/PRIME_OS_ROADMAP.md`

## Purpose

P1 First Light requires an unmistakably Prime graphical body rather than a stock Fedora/GNOME/KDE/COSMIC session. The frozen architecture already selects a custom Rust/Smithay compositor direction and a lightweight Rust Prime Shell host. This contract narrows that authority into the smallest implementation surface required to begin P1 without silently pulling later compatibility/runtime scope into the base image.

## Permanent process boundary

P1 keeps the three initial Prime services mechanically distinct:

```text
primed
  = Host-local machine authority / Prime Core

prime-compositor
  = Wayland display, output, input and window-composition authority

prime-shell
  = Prime-owned desktop/system UI client
```

`prime-shell` does not become Prime Core. It consumes versioned Prime capabilities and state through the existing Prime interface rather than reaching into `/var/lib/prime` or privileged kernel/device paths directly.

`prime-compositor` does not become a mission scheduler, application policy authority, updater, package manager, or cybersecurity engine.

## Smithay baseline

The implementation target is Smithay `0.7.0` or an exactly locked compatible revision proven by the P1 toolchain before merge.

Current upstream Smithay `0.7.0` declares Rust `1.87` as its minimum, so it is compatible in principle with Prime's pinned Rust `1.97.1`. The exact resolved graph must still be generated by the real pinned Prime toolchain and committed in `Cargo.lock`; it must not be hand-invented.

The minimum **production** Smithay feature target is conceptually equivalent to:

```text
backend_drm
backend_gbm
backend_libinput
backend_udev
backend_session_libseat
desktop
renderer_gl
wayland_frontend
```

with Smithay default features disabled so P1 does not automatically pull unrelated backends/features merely because upstream enables them by default.

P1 production does **not** require:

- `backend_winit`;
- `backend_x11`;
- XWayland;
- Vulkan rendering;
- multi-GPU rendering;
- Pixman fallback;
- nested-compositor operation.

Those may be introduced only when a later proof or explicit development fixture justifies them. A nested backend may be useful as a private construction/debug mechanism, but it is not the P1 physical acceptance path.

## Required native Linux facilities

Smithay's direct TTY/Udev/DRM path requires the Linux facilities represented upstream by:

- Wayland;
- xkbcommon;
- udev;
- libinput;
- GBM/DRM;
- libseat/session management;
- EGL/GLES for the initial renderer.

Prime must determine the exact Fedora 44 package names/versions from the pinned base during implementation proof. This contract intentionally does not guess package names from another distribution or Fedora release.

P1's physical graphics target is the HP 290 G4 proof Host with Intel UHD Graphics 630. The initial renderer therefore prioritizes the normal Mesa/DRM/GBM/EGL path required for that Host rather than adding multiple rendering stacks before evidence demands them.

## Compositor responsibilities

`prime-compositor` owns only the mechanical graphical/session responsibilities necessary for P1:

- acquire/release the active seat through the proven session mechanism;
- enumerate DRM devices/connectors through udev;
- establish the selected output mode;
- initialize GBM/EGL/GLES rendering;
- establish a Wayland display/socket;
- accept Wayland clients;
- route libinput keyboard/pointer events;
- maintain focus and basic window placement;
- render mapped surfaces and Prime Shell layers;
- survive/reconcile output/input hotplug within P1 bounds;
- expose truthful degraded/failure state rather than silently falling back to a stock desktop.

The compositor must not require root merely as an implementation shortcut where the selected seat/session mechanism can grant the required devices safely. Exact service/session credentials are a live-proof decision because they must be validated against Fedora 44/systemd/logind/libseat on the proof Host.

## Prime Shell responsibilities

`prime-shell` is a compositor client and owns the visible P1 system body:

- Prime startup transition after the compositor becomes ready;
- desktop/background surface;
- system rail;
- Prime Orb/launcher baseline;
- application launching from Prime Application Profile/capability truth;
- window/task representation;
- notification surface baseline;
- quick controls;
- network status/control surface;
- audio status/control surface;
- power/battery/thermal summary where mechanically available;
- hardware-health summary;
- settings entry surface;
- restart/shutdown entry points through authorized Prime/system mechanisms;
- update/generation status visibility without implementing P1.5 update mutation inside Shell;
- clear degraded-state reporting when optional capabilities are unavailable.

P1 Shell may use native Rust rendering for compositor-owned/simple shell surfaces and may later host richer React/TypeScript surfaces through a lightweight Rust/system-WebKit path where justified by the frozen architecture. Electron is not a mandatory P1 dependency.

## Prime Orb baseline

The P1 Orb is a Prime-owned launcher/system entry point, not an AI/runtime scheduler.

Minimum P1 behavior:

- open/close deterministically from pointer and keyboard input;
- list available Prime application/profile entries without inventing compatibility;
- launch an admitted application through Prime Exec rather than direct arbitrary process execution;
- surface Settings, power/restart and recovery guidance;
- show disabled/unavailable entries truthfully when the underlying capability is absent;
- preserve keyboard navigation and focus semantics.

Hunter/Origins/Ptah mission semantics do not move into the Orb during P1.

## Failure isolation

P1 must earn these negative controls:

- killing/restarting `prime-shell` must not destroy Prime Core or Host state;
- a Shell crash must not turn into a fake successful application operation;
- `prime-compositor` failure must be distinguishable from Shell failure;
- the separate recovery UKI/`prime-recovery.target` must remain reachable without either graphical service;
- if no supported DRM output can be established, Prime reports a graphical failure rather than starting Fedora's stock desktop;
- if the input stack cannot be established, the failure is explicit and recovery remains independent.

## Service ordering target

The eventual systemd relationship must preserve this direction:

```text
Prime Core ready
      ↓
prime-compositor ready
      ↓
Wayland socket/display ready
      ↓
prime-shell starts
      ↓
Prime visual-ready gate
```

Readiness must be mechanical. A process merely existing is not sufficient evidence that an output has been configured or that the Shell has rendered its first accepted frame.

The exact readiness primitive may be a runtime state/socket/notification mechanism, but it must not create a second machine-authority database or bypass Prime Core.

## Development proof ladder

The implementation may earn responsibility progressively:

1. compile against the exact locked Smithay graph;
2. unit/static proof for state/focus/layout logic;
3. nested development backend only if useful for fast visual iteration;
4. direct TTY Udev/DRM backend on the real Prime/Fedora substrate;
5. Intel UHD 630 output + input evidence on HP/Kratos;
6. basic Wayland client map/unmap/focus proof;
7. Prime Shell/system rail/Orb render proof;
8. Shell restart/failure isolation proof;
9. owner visual acceptance against Prime's reference/design language.

Only steps using the direct physical backend count toward P1 Host graphics acceptance.

## Dependency-lock gate

Before any Smithay code is merged into the P1 candidate:

- use the pinned Rust/Cargo toolchain;
- resolve the smallest feature set above;
- record the resulting exact `Cargo.lock` changes;
- record native build dependencies required by the pinned Fedora 44 base;
- run `cargo metadata --locked`;
- review transitive dependencies and feature activation;
- reject accidental XWayland/Vulkan/nested-backend expansion unless explicitly justified;
- freeze the exact candidate before proof.

A manually fabricated lockfile is not acceptable evidence.

## P1 visual acceptance gate

P1 is not complete merely because Smithay displays a surface. The accepted candidate must visibly provide:

- Prime product identity at startup;
- Prime Shell rather than stock distro UI;
- functional windowing;
- system rail;
- Orb/launcher;
- quick controls;
- smooth core transitions on the proof Host;
- Prime glass/depth language at the accepted P1 level;
- no obvious Fedora/GNOME/KDE/COSMIC identity leakage;
- owner visual acceptance.

## Non-claims

This contract does not implement or claim:

- Windows Personality;
- Android Personality;
- XWayland compatibility;
- arbitrary desktop-environment compatibility;
- Prime Store/component delivery;
- Hunter/Origins/Ptah UI integration;
- multi-GPU support;
- HDR/color-management completeness;
- remote/distributed display;
- final accessibility completeness beyond the P1 baseline;
- P1.5 update/survival completion.
